# Supabase database management

All database changes belong in `supabase/migrations/` and should be applied in
order by the Supabase CLI. Do not edit a migration that has already been
applied to a shared or production database; create a new migration instead.

## Local setup

Install the [Supabase CLI](https://supabase.com/docs/guides/cli), then from the
repository root:

```bash
supabase start
supabase db reset
```

`db reset` recreates the local database from the migration files. It is
destructive to the local Supabase database only.

## Create and apply migrations

```bash
supabase migration new describe_the_change
supabase db reset
supabase db push
```

Use `supabase db diff -f describe_the_change` when generating a migration from
changes made to a local database. Review the generated SQL before committing
it.

## Link a hosted project

```bash
supabase login
supabase link --project-ref <your-project-ref>
supabase migration list
supabase db push
```

The existing `001_initial_schema.sql` is the repository's baseline migration.
It is intentionally left unchanged until we confirm whether it has already
been applied to a hosted project. New migrations should use the timestamped
names generated by `supabase migration new`.

## Bootstrap the superadmin account

Migration `20260924055306_superadmin_and_event_source.sql` adds a trigger that
creates a `public.profiles` row for every new `auth.users` row, seeds the single
studio with the fixed id `00000000-0000-0000-0000-000000000001`, and adds
`public.promote_to_superadmin(text)`.

Every new user starts as `client`. Promotion is explicit and manual:

1. In the Supabase dashboard, open **Authentication → Users → Add user** and
   create the studio account with an email and password. **Do not put the
   password in this repository, in a migration, or in `.env`.**
2. Confirm a `public.profiles` row appeared automatically for that user.
3. Promote it:

   ```sql
   select public.promote_to_superadmin('you@example.com');
   ```

4. Set the same address as `SUPERADMIN_EMAIL` in `backend/.env` and
   `VITE_SUPERADMIN_EMAIL` in `.env.local`.

`SUPERADMIN_EMAIL` is authoritative for the API; `profiles.role` is what RLS
reads. Change one without the other and access breaks silently — see
`standards/divineApertureApp/backend/superadmin-allowlist.md`.

Public signup must stay disabled (ADR-007). Turn off email signups under
**Authentication → Providers → Email** so the allowlist is the only way in.

## Google Drive access

Importing reads a Drive folder with either credential, preferring the service
account:

- `GOOGLE_SERVICE_ACCOUNT_FILE` — path to a service-account JSON key. Also
  reads folders **shared with the service account**, not only world-readable
  ones. Share a folder with the account's `client_email` to grant access.
- `GOOGLE_API_KEY` — fallback; only reads folders shared as "anyone with the
  link".

**The key file must never be committed.** `.gitignore` covers
`service-account*.json`; keep the file at mode 600. Rotate the key in Google
Cloud IAM if it is ever pasted into a chat, a ticket, or a log.

### Why photos are proxied, not hotlinked

`GET /api/images/{token}` fetches Google's *rendered preview* of each file and
streams it. Three reasons, all found the hard way against a real 546-file
folder:

1. Real shoot folders are mostly RAW and HEIF — 337 of 546 in the first one —
   which no browser can display. The preview endpoint transcodes everything
   to JPEG.
2. The originals were 6.1 GB. Previews are ~20–100 KB each.
3. Google throttles hotlinked Drive images (429 with an HTML body). Fetching
   server-side once per (photo, width) and caching avoids it.

Tokens are HMAC-signed and expire after 6 hours, so the bytes stay behind a
session rather than on a public URL.
